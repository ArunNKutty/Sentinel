Not VMs — host-side constructs

Routers and NATs are network namespaces with iptables rules on the host, not full VMs. They're lightweight network constructs that endpoints connect through.

Topology YAML — see M4.7 Host VMs and their NE pairings ("which NE protects which host") are expressed in the topology section of plasma.yaml — full schema in M4.7. M1–M4 examples are NE-only because the topology DSL doesn't land until M4.7. Atom is always co-resident in the NE; the split-host variant (Atom on a host VM, k-eth driver on the NE) is deferred — not in this plan.
Fabric exception Every other VM follows the host-NE pairing rule. The Fabric VM is the one exception — it carries the NE stack (Atom + kwark + gluon) inside the Fabric VM itself, so it doesn't need a separate NE in front. The Fabric Go backend talks to the Plasma daemon's REST API to drive fleet operations from the UI.

PlanePurposeParticipants
DataProtected endpoint traffic. NE is a transparent bump-in-the-wire — sits between the protected endpoint and the network. Endpoints don't address the NE; its presence is invisible to them.Host VMs, routers, NATs ↔ NE VMs
ControlAtom ↔ Atom signaling between NEs (peer state, session negotiation). Dedicated port.NE ↔ NE
ManagementFabric ↔ Atom on each NE. Out-of-band port for config, monitoring.Fabric VM ↔ all NE VMs

Step 2: Extract rootfs from WIC

bash
WIC="petalinux-sdimage.wic"
ROOTFS="/opt/plasma/images/rootfs-base.raw"

OFFSET=$(fdisk -l $WIC | awk '/Linux filesystem/{print $2}')
SIZE=$(fdisk -l $WIC | awk '/Linux filesystem/{print $4}')

mkdir -p /opt/plasma/images
dd if=$WIC of=$ROOTFS bs=512 skip=$OFFSET count=$SIZE
truncate -s 4G $ROOTFS
e2fsck -f $ROOTFS
resize2fs $ROOTFS

Step 3: Launch

bash
cloud-hypervisor \
  --kernel /opt/plasma/petalinux/Image \
  --cmdline "console=ttyAMA0 root=/dev/vda rw" \
  --disk path=/opt/plasma/images/rootfs-base.raw \
  --cpus boot=4 \
  --memory size=2G \
  --serial tty \
  --console off

Step 4: Verify

at the serial console
lsmod | grep kwark              # kwark loaded?
lsmod | grep gluon              # gluon loaded?
systemctl status atom            # Atom running?
dmesg | grep gennetlink          # gennetlink family registered?
x86_64 host? Cloud Hypervisor needs KVM — no software emulation. Confirm your host arch before M1. If x86_64, rebuild kernel + modules with ARCH=x86_64, Go binaries with GOARCH=amd64. All logic is identical.

✓ DONE WHEN

  • PetaLinux boots in ~200ms
  • kwark + gluon loaded, kwark↔gluon binding established

M2 — ne-agent

Go binary inside the guest. vsock port 9100. Three ops: health, exec, cp.

build + inject
# Build (arm64 — swap to amd64 if host is x86_64)
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o ne-agent -ldflags="-s -w" ./cmd/ne-agent

# Mount rootfs, inject, enable systemd service
sudo mount -o loop /opt/plasma/images/rootfs-base.raw /tmp/rootfs
sudo mkdir -p /tmp/rootfs/opt/ne/bin
sudo cp ne-agent /tmp/rootfs/opt/ne/bin/
sudo chmod +x /tmp/rootfs/opt/ne/bin/ne-agent

sudo tee /tmp/rootfs/etc/systemd/system/ne-agent.service << 'EOF'
[Unit]
Description=NE Agent
After=network.target
[Service]
ExecStart=/opt/ne/bin/ne-agent
Restart=always
[Install]
WantedBy=multi-user.target
EOF
sudo chroot /tmp/rootfs systemctl enable ne-agent
sudo umount /tmp/rootfs

M4.6 — Snapshot / restore

Cloud Hypervisor supports VM snapshots natively. Plasma exposes them as fleet-aware operations — snapshot a 50-VM baseline, run destructive tests, restore in seconds. Restore beats reboot by ~10×.

CLI
plasma snapshot create baseline
[+] Snapshotting 50 VMs ...
[+] Done in 4.2s. Snapshot: baseline (3.4 GB)

plasma snapshot list
NAME      VMS  CREATED              SIZE
baseline  50   2026-04-27 14:02:11  3.4 GB

plasma snapshot restore baseline
[+] Restored 50 VMs in 1.6s

# Per-VM snapshot
plasma snapshot create one-vm --vm ne-00

plasma snapshot delete baseline

Why this matters

  • Iterating on M5 image profiles or M6 module reloads gets ~10× faster — restore beats reboot.
  • Captures the exact state Atom + kwark + gluon left behind, including running gennetlink sessions.
  • Test runs become deterministic — same baseline, same starting point, every time.
Storage layout Each snapshot is a CH memory dump + disk overlay diff. Per-VM ~50–100 MB. A 50-VM snapshot is ~3–5 GB. Persisted to /opt/plasma/snapshots/<name>/ so they survive plasma down + plasma up.

✓ DONE WHEN

  • plasma snapshot create baseline on a 50-VM fleet completes
  • plasma snapshot restore baseline brings everything back in <3s
  • Snapshots survive plasma down / plasma up
  • Per-VM and whole-fleet snapshots both work

M4.7 — Topology DSL

plasma.yaml grows top-level blocks for declarative topology — shape borrowed from containerlab, adapted to our three-plane model and the NE bump-in-the-wire. Defaults handle the common case so most setups never write a links entry.

Top-level shape

plasma.yaml
name: defense-mesh

# Auto-managed bridges, one per plane.
planes:
  data:    { bridge: br-data, cidr: "10.0.0.0/16"   }
  control: { bridge: br-ctrl, cidr: "10.1.0.0/16"   }
  mgmt:    { bridge: br-mgmt, cidr: "172.16.0.0/24" }

# VMs by role. 'count' expands fleets (ne-00 ... ne-49).
nodes:
  fabric-00:
    role: fabric
    image: "/opt/plasma/images/fabric-master.raw"
    resources: { vcpu: 4, ram_mb: 4096 }
    ne: { modules: ["kwark.ko", "gluon.ko"], atom: co-resident }
    fabric: { docker_image: "...", ui_port: 3000, api_port: 8443 }

  ne:
    role: ne
    count: 50
    image: "/opt/plasma/factory/output/ne-defense.raw"
    resources: { vcpu: 4, ram_mb: 1536 }
    ne: { modules: ["kwark.ko", "gluon.ko"], atom: co-resident }

  host:
    role: host
    count: 50
    image: "/opt/plasma/images/alpine-host.raw"
    resources: { vcpu: 2, ram_mb: 512 }
    workload: { cmd: "iperf3 -s" }    # optional

# Host-side network constructs (NOT VMs — namespaces + iptables).
constructs:
  edge-router:  { kind: router, interfaces: [lan, wan] }
  internet-nat: { kind: nat,    upstream: "10.0.0.0/24" }

# NE -> endpoint pairing. Defines who sits transparently in front of whom.
pairings:
  - { ne: "ne[*]", endpoint: "host[*]", scheme: zip }
  # or one-off: { ne: ne-00, endpoint: edge-router }

# Custom links override defaults. Most setups leave this empty.
links: []

What plasma up does on parse

startup pipeline
1. Validate node refs in pairings, expand 'count' into named instances
2. Create plane bridges (br-data, br-ctrl, br-mgmt) with CIDR allocation
3. Create router/NAT namespaces from constructs (iptables rules, routes)
4. For each pairing, wire NE's data-in iface to the paired endpoint
5. Auto-attach each VM's plane interfaces to plane bridges
6. Apply explicit 'links' overrides last
7. Launch VMs in dependency order (fabric & NEs before hosts)

Containerlab influence — what we kept and what we changed

From containerlabPlasma adaptation
nodes / links / endpointsSame shape
kind discriminatorRenamed to role (fabric/ne/host)
image, resources per nodeSame
Container-only by default; VMs via vrnetlab+QEMUDirect Cloud Hypervisor — keeps boot speed and density
No native pairing concept (every link is explicit)New pairings block — declarative NE↔endpoint binding with scheme: zip for fleets
Routers/NATs as container nodesNew constructs block — host namespaces, lighter than VMs
No plane abstractionNew planes block — auto-attach to data/ctrl/mgmt bridges, no links needed for the common case
Defaults handle 80% of cases 50 NEs + 50 hosts + a one-line pairings entry — done. Reach for links only for non-default arrangements (star, segmented mesh, multi-bridge data plane).

✓ DONE WHEN

  • plasma.yaml validates and parses the new top-level keys (planes, nodes, constructs, pairings, links)
  • Default plane bridges + CIDR allocation come up without any links entries
  • NE↔host pairing wires the NE's data-in interface to the host's data interface (transparent bump)
  • count expands fleets correctly, names follow <group>-NN
  • Routers/NATs come up as namespaces with iptables rules — endpoints behind them route correctly
  • Existing M1–M4.6 YAML still works (backwards-compatible with the simpler host_groups form, or auto-migrated)

M6 — Module hot-reload

CLI
# Full fleet
plasma module push kwark.ko --restart-atom
ne-00: ✓ 58ms ... ne-49: ✓ 55ms
Summary: 50/50 success, 1.8s

# Single target
plasma module push kwark.ko --target ne-00 --restart-atom

# Canary → fleet
plasma module push kwark.ko --target ne-00,ne-01,ne-02 --restart-atom
plasma vm health ne-00   # check kwark_gluon_bound
plasma module push kwark.ko --restart-atom

Reload sequence inside guest

ne-agent handles this
1. Stop Atom (holds gennetlink socket)
2. rmmod kwark         (unbinds from gluon)
3. Write new kwark.ko
4. insmod kwark.ko mode=sim
5. Verify kwark↔gluon binding re-established
6. Restart Atom
7. Verify gennetlink connected
gluon stays loaded Only kwark is reloaded. gluon remains in the kernel. kwark re-binds to gluon on insmod via the direct kernel API. If gluon also changes, reload both: rmmod kwark → rmmod gluon → insmod gluon → insmod kwark.

Makefile

Makefile
KDIR ?= /opt/plasma/petalinux/kernel-source

build:
	make -C $(KDIR) M=$(PWD) ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- modules

reload: build
	plasma module push kwark.ko --restart-atom

reload-one: build
	plasma module push kwark.ko --target ne-00 --restart-atom

test: reload-one
	plasma vm exec ne-00 -- /opt/ne/bin/ne-test --genl-smoke

logs:
	plasma vm logs ne-00 --follow

✓ DONE WHEN

  • make reload pushes kwark to all VMs in <3s
  • kwark↔gluon binding re-establishes
  • Atom reconnects via gennetlink

M7 — Fabric

An Alpine or Ubuntu VM that co-locates the NE stack (Atom + kwark + gluon) with the Fabric application. Docker runs on top to host the Fabric Next.js UI + Go backend. The Fabric backend drives the fleet by calling the Plasma daemon's REST API; operators interact via the UI.

Two kernels, two module builds NE VMs run PetaLinux; the Fabric VM runs Alpine/Ubuntu. kwark and gluon are kernel-version-specific, so they're built twice — once against the PetaLinux kernel (drops onto NE VMs) and once against the Alpine/Ubuntu kernel (drops onto the Fabric VM). Atom is userspace and ships unchanged.

What Fabric does

  • UI for operators to configure, connect to, and monitor the NE fleet
  • Pushes policies and crypto config to each NE's Atom
  • Aggregates health, session state, and telemetry from every Atom
  • Orchestrates rekey, firmware updates, fleet-wide operations
  • Go backend → Plasma REST API for VM-level operations (start/stop/snapshot/etc.)
Why the NE stack on Fabric? Fabric needs the same crypto stack as a regular NE so it can speak peer-to-peer with the fleet. Co-locating it on the Fabric VM (instead of pairing Fabric with a separate NE) keeps the topology simpler. This is the only VM that breaks the host-NE pairing rule.

YAML

plasma.yaml — with Fabric
host_groups:
  # Fabric master — NE stack + Docker + Fabric app, all in one VM
  - name: fabric
    role: fabric
    count: 1
    vcpu: 4
    ram_mb: 4096
    image: "/opt/plasma/images/fabric-master.raw"   # Alpine/Ubuntu + Docker
    ne:
      modules: ["kwark.ko", "gluon.ko"]
      module_params: {kwark: "mode=sim"}
      atom: co-resident
    fabric:
      docker_image: "ghcr.io/your-org/fabric:latest"
      ui_port: 3000
      api_port: 8443
      plasma_api: "http://<host>:8080"          # Plasma daemon REST

  # NE fleet
  - name: ne
    role: ne
    count: 20
    vcpu: 4
    ram_mb: 1536
    ne:
      modules: ["kwark.ko", "gluon.ko"]
      module_params: {kwark: "mode=sim"}
      atom: co-resident

Networking

The Fabric VM has its own NE stack, so it participates in all three planes: data (encrypted ops traffic to fleet NEs), control (Atom ↔ Atom session negotiation), and management (the Fabric app's UI/API). The Fabric backend additionally talks to the Plasma daemon REST API on the host to drive VM-level operations (start/stop/snapshot/etc.) — that's a side channel, not on any of the NE planes.
